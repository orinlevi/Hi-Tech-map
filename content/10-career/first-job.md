# 🎓 העבודה הראשונה -- מה לצפות

## למה זה חשוב

מזל טוב! עברתם את הראיונות, קיבלתם הצעה, חתמתם על חוזה, ועכשיו אתם עומדים מול המחשב ביום הראשון עם הרגשה של "מה לעזאזל אני עושה פה". זה **נורמלי לחלוטין**. כל מפתח/ת שאתם מכירים הרגיש/ה את זה. גם ה-CTO.

> "ביום הראשון בעבודה, ביקשו ממני לעשות clone ל-repo. לקח לי 20 דקות להבין למה ה-git clone לא עובד. התברר שלא הייתה לי הרשאת גישה. זה היה הרגע הכי מביך בחיי. היום אני צוחק על זה."

!!! note "הסוד הגדול של העבודה הראשונה"
    **אף אחד לא מצפה שתדעו הכל.** מה שכן מצפים: שתשאלו שאלות, שתלמדו מהר, ושלא תשברו production. (על האחרון -- ראו בהמשך.)

## Onboarding -- מה באמת קורה

### שבוע ראשון: הישרדות

**מה לצפות:**

- **הרבה Setup** -- התקנת סביבת עבודה, הרשאות, VPN, Slack, Jira, GitHub
- **הרבה מסמכים** -- קריאת documentation (שחלקו מיושן, שחלקו לא קיים)
- **הרבה שמות חדשים** -- אנשים, פרויקטים, ראשי תיבות פנימיים. אתם **תשכחו** 80% מהם. זה בסדר
- **הרבה ישיבות** -- intro meetings עם כולם. תביאו מחברת

> "בשבוע הראשון חשבתי שכולם מדברים שפה אחרת. PD, PRD, SLA, P0, OKR, retro, standup, grooming... לקח חודש להבין את כל הראשי תיבות."

!!! tip "טיפ ליום הראשון"
    1. **כתבו הכל** -- שמות, ראשי תיבות, links, הסברים. תודו לעצמכם בעוד שבוע
    2. **אל תנסו להרשים** -- אף אחד לא מצפה ממכם PR ביום הראשון
    3. **תכירו אנשים** -- ארוחת צהריים עם הצוות שווה יותר מ-10 שעות קריאת docs
    4. **תבקשו buddy** -- אם לא מציעים, תבקשו. מישהו שתוכלו לשאול "שאלות טיפשות"

---

### חודש ראשון: למידה

**מה לצפות:**

- **משימה ראשונה** -- בדרך כלל bug fix קטן או feature קטן. המטרה: שתכירו את ה-codebase
- **Code reviews** -- תקבלו הרבה הערות. זה **לא ביקורת** -- זה למידה
- **הרגשת אובדן** -- ה-codebase הוא ענק ומפחיד. זה נורמלי. אף אחד לא מבין את הכל
- **Pair programming** -- אולי תשבו עם מפתח Senior שיעבוד איתכם. נצלו את זה!

**ציפיות ריאליסטיות:**

| מה הם רוצים | מה הם **לא** רוצים |
|-------------|-------------------|
| שתשאלו שאלות | שתשבו בשקט 3 שעות בלי לבקש עזרה |
| שתלמדו מ-code reviews | שתיקחו ביקורת באופן אישי |
| שתעשו mistakes ותלמדו | שתשברו production בלי לספר לאף אחד |
| שתהיו proactive | שתחכו שיגידו לכם מה לעשות |

---

### 3-6 חודשים: תרומה

**מה קורה:**

- מתחילים לתרום features אמיתיים
- מבינים את ה-codebase (לפחות את החלק שלכם)
- מתחילים לעשות code reviews לאחרים
- מפסיקים לשאול "איפה זה?" ומתחילים לשאול "למה ככה?"

!!! note "אל תשוו את עצמכם"
    אחרי 3 חודשים אתם לא אמורים להיות ברמה של ה-Senior עם 5 שנות ניסיון. אתם אמורים להיות **טובים יותר ממה שהייתם לפני 3 חודשים**. זה הכל.

## Impostor Syndrome -- הפיל בחדר

Impostor syndrome -- כולם חושבים שהם לא מספיק טובים. חוץ מאלו שצריכים לחשוב ככה. בעבודה הראשונה, ההרגשה הזו מוכפלת פי 10.

### סימנים שאתם סובלים מ-Impostor Syndrome

- "הם יגלו שאני לא באמת יודע/ת לתכנת"
- "כולם יותר חכמים ממני"
- "קיבלו אותי בטעות"
- "אני לא שואל/ת שאלות כי לא רוצה להיראות טיפש/ה"

### מה עוזר

- **דברו על זה** -- תופתעו כמה אנשים בצוות מרגישים אותו דבר
- **כתבו יומן הישגים** -- כל שבוע, 3 דברים שלמדתם או עשיתם
- **הזכירו לעצמכם**: עברתם ראיון טכני. מישהו מקצועי החליט שאתם **מספיק טובים**. תסמכו עליהם
- **Pair programming** -- לעבוד עם מישהו Senior ולראות שגם הם googl-ים דברים

> "שנתיים בתור Senior, ואני עדיין מחפש ב-Google 'how to center a div'. Impostor syndrome הוא שקר."

## שאלות -- איך שואלים נכון

### למה שאלות חשובות

**שאלה טובה** חוסכת **שעות** של עבודה מיותרת. **שתיקה** גורמת לבזבוז זמן של כולם.

!!! warning "הטעות הכי נפוצה של Juniors"
    **לא לשאול שאלות.** מפחדים להיראות טיפשים, אז יושבים שעתיים תקועים. **אף אחד לא מצפה שתדעו הכל.** כולם מצפים שתשאלו.

### כלל ה-30 דקות

1. **תנסו לבד 30 דקות** -- קראו docs, חפשו ב-Google, בדקו את ה-codebase
2. **אחרי 30 דקות -- שאלו** -- "ניסיתי X, Y, Z. עדיין תקוע. יש לך כיוון?"
3. **הכלל**: "ניסיתי [מה שניסיתם]. קראתי [מה שקראתם]. אני חושב שהבעיה היא [השערה]. מה דעתך?"

### מבנה של שאלה טובה

| רכיב | דוגמה |
|------|-------|
| **הקשר** | "אני עובד/ת על ה-authentication feature" |
| **מה ניסיתי** | "ניסיתי להשתמש ב-JWT middleware, אבל ה-token לא מתאמת" |
| **מה אני חושב** | "אני חושב שהבעיה היא ב-secret key configuration" |
| **מה אני צריך** | "אפשר להסתכל על ה-config שלי ולהגיד לי אם אני מפספס משהו?" |

**שאלה גרועה**: "זה לא עובד, מה לעשות?"

**שאלה טובה**: "ה-JWT validation נכשל עם error X. בדקתי את ה-secret ב-env ואת ה-token expiry. אתה חושב שזה יכול להיות issue עם clock skew?"

## Code Review -- תרבות שכדאי לאמץ

### מה זה Code Review?

מישהו אחר בצוות **קורא את הקוד שכתבתם** לפני שהוא נכנס ל-codebase. זה אחד הדברים הכי חשובים בעבודת צוות.

### למה זה קיים

- **לתפוס bugs** לפני שהם מגיעים ל-production
- **לשמור על quality** -- קוד נקי, readable, maintainable
- **ללמד** -- גם הכותב וגם הקורא לומדים
- **לשתף ידע** -- אם רק אדם אחד מכיר קטע קוד, זו בעיה

### איך לקבל code review

!!! tip "כללים לקבלת Code Review"
    1. **אל תיקחו אישית** -- הערות על הקוד, לא עליכם
    2. **תגיבו לכל הערה** -- "תיקנתי", "שאלה טובה, הוספתי הערה", או "אני לא מסכים כי..."
    3. **תשאלו אם לא ברור** -- "אפשר להסביר למה הגישה הזו עדיפה?"
    4. **תכתבו PRs קטנים** -- PR של 50 שורות מקבל review יסודי. PR של 500 שורות מקבל LGTM ותפילה
    5. **תוסיפו תיאור** -- מה עשיתם, למה, ואיך לבדוק

### איך לתת code review (כשתגיעו לשלב הזה)

- **היו עניינים** -- "Consider using X instead of Y" עדיף על "Why did you do this?"
- **הסבירו למה** -- לא רק "change this", אלא "change this because..."
- **תמצאו גם דברים טובים** -- "Nice approach here!" עושה המון
- **היו consistent** -- אם יש style guide, תפנו אליו

## Git Workflow -- איך עובדים בצוות

### הזרימה הטיפוסית

```
main ← develop ← feature/my-feature
```

1. **Pull** -- מושכים את הקוד העדכני מ-main/develop
2. **Branch** -- יוצרים branch חדש לכל feature/bugfix
3. **Commit** -- commits קטנים ומתוארים היטב
4. **Push** -- דוחפים ל-remote
5. **PR (Pull Request)** -- פותחים PR ומבקשים code review
6. **Review** -- מתקנים הערות
7. **Merge** -- ה-PR מתמזג ל-main/develop
8. **Delete Branch** -- מוחקים את ה-feature branch

### כללים לעבודה עם Git

!!! warning "דברים שלא עושים (במיוחד בהתחלה)"
    - **לעולם אל תעשו force push ל-main** -- זה יכול למחוק עבודה של אחרים
    - **לעולם אל תעשו commit ישירות ל-main** -- תמיד דרך PR
    - **אל תעשו commit ל-secrets** -- passwords, API keys, tokens. השתמשו ב-.env ו-.gitignore
    - **אל תעשו commit של node_modules** -- גם על זה יש .gitignore

### Commit Messages

**טוב:**

- `fix: resolve login timeout issue (#123)`
- `feat: add dark mode toggle to settings`
- `refactor: extract validation logic to utils`

**רע:**

- `fix stuff`
- `asdfjkl`
- `FINAL version (for real this time)`

> "ה-commit message שלך צריך להסביר **למה** עשית את השינוי, לא **מה** עשית. ה-diff מראה מה. אתה צריך להסביר למה."

## Agile Basics -- מינימום שצריך לדעת

### מה זה Agile?

שיטת עבודה שמתמקדת ב-**iterations קצרים** (sprints) במקום תכנון ארוך מראש.

### המושגים החשובים

| מושג | מה זה | בשפה פשוטה |
|------|--------|-----------|
| **Sprint** | תקופת עבודה (1-4 שבועות) | "בשבועיים הקרובים, אנחנו מתמקדים ב-X" |
| **Standup** | פגישה יומית קצרה (15 דק') | "מה עשיתי אתמול, מה אני עושה היום, מה חוסם אותי" |
| **Backlog** | רשימת כל המשימות | "כל מה שצריך לעשות, מסודר לפי חשיבות" |
| **Sprint Planning** | תכנון תחילת ספרינט | "מה נספיק לעשות בספרינט הזה?" |
| **Retro** | מפגש סיום ספרינט | "מה הלך טוב? מה לשפר? מה לעצור?" |
| **Ticket / Story** | משימה בודדת | "כ-user, אני רוצה X כדי Y" |
| **PR** | Pull Request | "תסתכלו על הקוד שלי לפני שנכניס" |

### טיפים ל-Standup

- **קצר** -- 30 שניות לכל אחד, לא 5 דקות
- **ממוקד** -- אתמול / היום / חסימות. **לא** דיון טכני
- **כנות** -- אם אתם תקועים, תגידו. לא בושה

> "Standup הוא לא פגישה. זה sync. אם זה לוקח יותר מ-15 דקות -- משהו לא עובד."

## Mentorship -- מנטור זה לא מותרות

### למה צריך מנטור

- **מקצר את עקומת הלמידה** -- מה שלוקח חודש לבד, לוקח שבוע עם מנטור
- **מונע טעויות** -- "אל תעשה X, אני כבר עשיתי את הטעות הזו"
- **פרספקטיבה** -- רואה את הקריירה שלכם ממקום אחר
- **רשת קשרים** -- מכיר אנשים שאתם לא מכירים

### איך מוצאים מנטור

1. **בתוך החברה** -- Senior בצוות, מנהל ישיר, או מישהו מצוות אחר
2. **בקהילה** -- meetups, Discord, LinkedIn. פנו בעדינות: "אשמח לשאול כמה שאלות"
3. **אל תבקשו "תהיה לי מנטור"** -- זה מפחיד. תבקשו שיחה של 20 דקות, ותגידו שהייתה מועילה

!!! tip "איך להיות mentee טוב"
    - **הגיעו מוכנים** -- אל תגיעו בלי שאלות ספציפיות
    - **כבדו את הזמן** -- 30 דקות, פעם בשבוע/שבועיים
    - **עדכנו** -- "עשיתי מה שהמלצת, והנה מה שקרה"
    - **הודו** -- אנשים עוזרים למי שמודה להם

## טעויות נפוצות של Juniors

### טעויות טכניות

!!! warning "10 טעויות שכולם עושים"
    1. **לא כותבים tests** -- "אין לי זמן". יש לכם עוד פחות זמן לתקן bugs ב-production
    2. **PRs ענקיים** -- PR של 1,000 שורות. אף אחד לא יעשה review רציני. תפצלו
    3. **לא קוראים logs** -- ה-error message בדרך כלל **אומר לכם** מה הבעיה
    4. **Over-engineering** -- בונים "מערכת גנרית" ל-feature פשוט. YAGNI (You Ain't Gonna Need It)
    5. **Copy-paste מ-Stack Overflow** -- בלי להבין מה הקוד עושה. זה מתפוצץ, ואתם לא יודעים למה
    6. **לא משתמשים ב-debugger** -- `print("here1")`, `print("here2")`. תלמדו debugger
    7. **Commit של secrets** -- API keys ב-GitHub. אחרי push -- כבר מאוחר. תשנו את ה-key
    8. **לא שואלים** -- יושבים 3 שעות תקועים. אחרי 30 דקות -- תשאלו
    9. **לא כותבים documentation** -- "הקוד מסביר את עצמו". לא, הוא לא
    10. **לא עושים backup** -- git stash, git commit, שמירה לפני שינויים גדולים. **תמיד**

### טעויות אנושיות

- **לא לבקש עזרה** -- זה לא חולשה. זה חוכמה
- **להשוות את עצמכם ל-Senior** -- אחרי 3 חודשים. הם עובדים 5 שנים
- **לא להציב גבולות** -- "אני חדש, אז אני חייב לעבוד 12 שעות". **לא**
- **לא לתעד** -- "אני אזכור". לא, לא תזכרו
- **להתבייש לומר 'לא ידעתי'** -- אמירת "לא ידעתי, עכשיו אני יודע" היא סימן לבגרות

## Work-Life Balance בהייטק הישראלי

### המציאות

הייטק ישראלי ידוע בשעות ארוכות. אבל זה **משתנה מחברה לחברה**, ולפעמים **מצוות לצוות**.

### מה נורמלי

| סוג חברה | שעות טיפוסיות | תרבות |
|----------|--------------|-------|
| סטארט-אפ מוקדם (Pre-Seed) | 9-10+ שעות/יום | "אנחנו משנים את העולם" |
| סטארט-אפ צומח (Series A-C) | 9-10 שעות/יום | אינטנסיבי אבל פחות קיצוני |
| חברה גדולה (Enterprise) | 8-9 שעות/יום | מובנה, פחות לחץ |
| R&D Center (Google, Meta, etc.) | 8-9 שעות/יום | יחסית רגוע, benefits מצוינים |

!!! note "אל תשרפו את עצמכם"
    **Burnout הוא אמיתי** ונפוץ בהייטק. סימנים: עייפות כרונית, חוסר מוטיבציה, ציניות, טעויות מרובות.

    **מה עוזר:**

    - הציבו גבולות -- גם אם אתם חדשים. "אני עובד עד 19:00" זה בסדר
    - קחו הפסקות -- Pomodoro (25 דקות עבודה, 5 דקות הפסקה)
    - אל תעבדו בסופ"ש -- אלא אם חייבים (production down)
    - דברו עם המנהל -- אם העומס לא סביר, תגידו

### טיפים ל-Work-Life Balance

1. **אל תבדקו Slack/Teams אחרי שעות** -- העולם ישרוד בלעדיכם עד הבוקר
2. **יש חיים מחוץ לקוד** -- תחביבים, ספורט, חברים. זה הופך אתכם למפתחים **טובים יותר**
3. **למדו להגיד "לא"** -- "אין לי bandwidth עכשיו" הוא משפט לגיטימי
4. **תנצלו את ה-perks** -- חדר כושר? ארוחות? תשתמשו
5. **חופשה היא לא מותרות** -- קחו חופש. תחזרו רעננים ויצרניים יותר

## 🛤️ מאיפה מתחילים

### 90 יום ראשונים -- תוכנית פעולה

**שבוע 1-2: Onboarding**

- [ ] התקינו את סביבת העבודה -- אם לא עובד, בקשו עזרה מיד
- [ ] הכירו את הצוות -- ארוחת צהריים עם כל אחד
- [ ] קראו את ה-README של הפרויקט
- [ ] הכינו מחברת/Notion לתיעוד דברים חדשים

**שבוע 3-4: משימות ראשונות**

- [ ] סיימו את ה-first task (גם אם זה bug fix קטן)
- [ ] פתחו את ה-PR הראשון -- אל תפחדו מ-comments
- [ ] הבינו את ה-git workflow של הצוות
- [ ] מצאו buddy או מנטור

**חודש 2: העמקה**

- [ ] הבינו חלק אחד של ה-codebase לעומק
- [ ] התחילו לתרום features קטנים
- [ ] תשאלו "למה?" ולא רק "איך?"
- [ ] התחילו לעשות code reviews (אם מרשים)

**חודש 3: תרומה**

- [ ] קחו ownership על feature או area
- [ ] הציעו שיפור ל-codebase (refactor, docs, tests)
- [ ] שתפו ידע -- כתבו doc, עשו הרצאה קצרה לצוות
- [ ] בקשו feedback מהמנהל -- "איפה אני יכול להשתפר?"

## 💼 שאלות לראיון עבודה

??? tip "מה היה האתגר הכי גדול בעבודה הראשונה שלך?"
    **מה באמת שואלים**: האם אתה לומד מניסיון ויכול להתמודד עם קשיים?

    **מבנה STAR:**

    - **Situation**: "בשבוע השלישי, ביקשו ממני לתקן bug ב-microservice שלא הכרתי"
    - **Task**: "הייתי צריך להבין את ה-flow ולמצוא את מקור הבעיה"
    - **Action**: "קראתי logs, עשיתי debugging, ואחרי שלא הצלחתי -- ביקשתי pair programming"
    - **Result**: "תיקנתי את ה-bug ב-2 ימים, ולמדתי את ה-service לעומק"

??? tip "איך אתה מתמודד עם code review קשה?"
    **מה באמת שואלים**: האם אתה מקבל feedback בצורה בוגרת?

    **תשובה טובה**: "אני מסתכל על code review כהזדמנות ללמוד. אם לא מסכים, אני שואל שאלות ומנסה להבין את הפרספקטיבה. אם עדיין לא מסכים, אני מסביר את הנימוקים שלי בצורה מכבדת."

    **תשובה גרועה**: "אני תמיד מסכים עם ה-reviewer" (לא אמין) או "בדרך כלל ה-reviewer טועה" (דגל אדום).

??? tip "ספר/י על טעות שעשית בעבודה"
    **מה באמת שואלים**: יש לך מודעות עצמית? אתה לוקח אחריות?

    **מבנה מנצח:**

    1. טעות ספציפית (לא "אני פרפקציוניסט")
    2. מה ההשפעה הייתה
    3. מה עשיתם כדי לתקן
    4. מה למדתם -- **ומה שיניתם** כדי שזה לא יקרה שוב

    **דוגמה**: "דחפתי config שגוי ל-production, מה שגרם ל-downtime של 10 דקות. למדתי לבדוק config changes ב-staging קודם, והוספתי automated validation."

??? tip "איך אתה לומד טכנולוגיה חדשה?"
    **מה באמת שואלים**: האם תמשיך ללמוד אחרי שנקבל אותך?

    **מבנה:**

    1. "קודם אני קורא את ה-documentation הרשמי -- getting started"
    2. "בונה פרויקט קטן כדי להרגיש את הטכנולוגיה"
    3. "קורא source code של פרויקטים אמיתיים"
    4. "שואל שאלות בקהילה (Discord, Stack Overflow)"

    ציינו דוגמה ספציפית: "ככה למדתי Docker -- בניתי container לפרויקט הצד שלי תוך שבוע."

??? tip "איך אתה מתעדף משימות?"
    **מה באמת שואלים**: האם תוכל לנהל את הזמן שלך?

    **מבנה:**

    1. "מסתכל על urgency vs importance (מטריצת Eisenhower)"
    2. "בודק עם ה-team lead אם יש priorities שהשתנו"
    3. "מפרק משימות גדולות לחלקים קטנים"
    4. "מתקשר אם אני חושב שלא אספיק ב-deadline"

    **הנקודה**: הם רוצים לדעת שלא תיתקעו בלי לבקש עזרה.

??? tip "מה חשוב לך במקום עבודה?"
    **מה באמת שואלים**: האם תתאים לתרבות שלנו?

    **תהיו כנים** (אבל טקטיים):

    - "צוות שלומד ומשתף ידע" -- תמיד רלוונטי
    - "Code review culture -- חשוב לי שהקוד שלי ייבדק וגם שאוכל לבדוק של אחרים"
    - "אוטונומיה עם support -- אני רוצה חופש לפתור בעיות, עם מנטור שמכוון"

    **אל תגידו**: "עבודה מהבית בלבד ולא יותר מ-6 שעות ביום" (גם אם זה מה שרוצים).

## בלבולים נפוצים

!!! warning "\"צריך לדעת את כל ה-codebase\""
    **לא ולא.** אף אחד לא מכיר את כל ה-codebase. גם לא ה-CTO. למדו את החלק שרלוונטי למשימות שלכם, וגדלו משם.

!!! warning "\"אם אני שואל שאלות, אני חלש\""
    **ההפך!** Junior ששואל שאלות = Junior שלומד מהר. Junior שלא שואל = Junior שתקוע בשקט. המנהלים שלכם **מעדיפים** שתשאלו.

!!! warning "\"אני חייב לעבוד יותר מכולם כי אני חדש\""
    **לא.** אתם חייבים **ללמוד** יותר, לא **לעבוד** יותר. שעה של למידה ממוקדת שווה יותר מ-3 שעות של spinning wheels.
