# Git Worktrees — עבודה מקבילה על אותו ריפו

## למה זה בכלל עניין?

דמייני שאת עובדת על ריפו גדול, ובמקביל רצים 5 תהליכים שונים (סשנים של Claude Code, עמיתים לצוות, סקריפטים אוטומטיים) — **כולם באותה תיקייה בפיינדר**, כולם מריצים פקודות git. בשלב מסוים מישהו עושה `git checkout` לענף אחר, וקבצים שהיו על המסך נעלמים. מישהו אחר מריץ `git merge` ומיזג למקום הלא נכון. התוצאה: בלגן, קבצים "נעלמים", עבודה הולכת לאיבוד.

זה לא באג של git — git פשוט לא תוכנן לשני תהליכים באותה תיקייה בו-זמנית.

## המודל המנטלי של git

שלושה רבדים נפרדים:

| רובד | מה זה | איפה זה חי |
|------|-------|------------|
| **מסד הנתונים של git** (`.git/`) | מחסן קבוע של כל הענפים, כל הקומיטים, כל הגרסאות | על הדיסק, מוסתר |
| **עץ עבודה** (working tree) | התצוגה של ענף אחד בכל רגע נתון — מה שרואים בפיינדר | על הדיסק, גלוי |
| **אזור ה-staging** (`.git/index`) | מה שעומד להיכנס לקומיט הבא | על הדיסק, מוסתר |

הרעיון המרכזי: **ענפים הם לא תיקיות.** ענף = קו זמן של קומיטים. כל קומיט = צילום של **כל הריפו** (לא של ענף אחד). כש-`git checkout` עובר לענף אחר, git מוחק מהדיסק קבצים שלא קיימים בקומיט של הענף החדש, ומכניס במקומם את הגרסאות שלהם. **הקבצים הישנים לא נמחקים — הם עדיין קיימים ב-`.git/`.** רק התצוגה השתנתה.

## הבעיה עם עבודה מקבילה

`.git/index` נעול בזמן כתיבה — שני תהליכים לא יכולים לכתוב אליו יחד. **אבל עץ העבודה עצמו לא נעול.** שני תהליכים שעושים `checkout` במקביל יכולים להתערבב, ולהשאיר קבצים חסרים על הדיסק למרות שגיט עצמו עדיין יודע שהם אמורים להיות שם.

זה מה שנקרא **race condition** (מצב מירוץ): שני תהליכים מתחרים על אותו משאב, והתוצאה תלויה במי מגיע ראשון לכל שלב.

## הפתרון: git worktrees

`git worktree` מאפשר ליצור **תיקייה פיזית נוספת** על הדיסק, קשורה לאותו ריפו אבל עומדת על ענף משלה. שתי תיקיות = שני "חלונות תצוגה" עצמאיים על מסד הנתונים המשותף.

```bash
# יצירת worktree חדש על ענף חדש
git worktree add ../worktrees/my-feature -b feature/my-work main

# מעבר לתיקייה החדשה
cd ../worktrees/my-feature
# עורכים, מקמיטים, דוחפים — הכל מבודד מתיקיות אחרות

# כשמסיימים
cd -
git worktree remove ../worktrees/my-feature
```

- **מסד הנתונים (`.git/`) משותף** — קומיטים נראים בכל ה-worktrees מיד
- **עצי העבודה נפרדים** — כל אחד רואה רק את הענף שלו
- אי אפשר ליצור שני worktrees על אותו ענף — זה מונע התנגשות לוגית

## מתי חייבים worktree?

**תמיד.** אם יש יותר מתהליך אחד שנוגע באותו ריפו (אנושי, סוכן AI, סקריפט) — כולם חייבים לרוץ ב-worktrees נפרדים. גם אם נראה שהתיקון קטן, גם אם "בטוח שאף אחד אחר לא עובד על זה כרגע". עלות היצירה (שלוש פקודות) זניחה; עלות של עבודה שהלכה לאיבוד גבוהה בהרבה.

## פקודות הצלה כשמשהו השתבש

```bash
git status                      # מה גיט חושב שאמור להיות על הדיסק
git restore <path>              # לשחזר קובץ שנעלם מהתצוגה
git branch --show-current       # לוודא על איזה ענף את לפני פעולה הרסנית
git rev-parse main              # לבדוק לאן main מצביע מקומית
git rev-parse origin/main       # לבדוק לאן main מצביע בשרת
git cherry-pick <commit>        # להעתיק קומיט שקומיטת לענף הלא נכון
```

## המסקנה

עבודה מקבילה על אותו ריפו בלי worktrees = מתכון לאיבוד עבודה. worktrees = בידוד פיזי על הדיסק שמונע את כל משפחת הבעיות הזו. זה לא אובר-הנדסה — זה אבטחה בסיסית לכל ריפו שיש בו יותר מסוכן אחד.
